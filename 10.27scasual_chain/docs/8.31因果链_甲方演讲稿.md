# 8.31 因果链 甲方介绍（照读稿）

各位好。今天介绍两版因果链代码，都在同一个仓库里，目录分开。先讲较早的 5.31，再讲当前的 8.31。两版都按三部分说：代码、数据集、其他文档。都不做五佳球、十佳球。

## 第一部分：5.31causal_chain

5.31 是中期测试包，只做拆条，没有集锦，也没有在线流式。

代码在 algo/causal_chain4。做法是：把一条已经切好的标注事件序列送进分类器，判断它属于哪一个因果链模板、哪一个大类。大类同样是结果、修正、险情、特殊。它不从整场时间线里自己找片段，时间、开头事件、结尾事件直接用这条标注自己的事件。所以它主要考的是“类别和模板分得对不对”，不是“从一场比赛里把链找出来”。评测入口是 eval/run_eval.py，可以纯规则，也可以加 Qwen。

数据集和后面 8.31 是同一批交付，63 场，拆条标准答案 437 条，在 datasets 目录。每一场主要是 strip_gold.json，timeline.json 有一份，但 5.31 的分类不依赖整场时间线。没有集锦标注。原始交付在 data/交付_out，需要时可以用 scripts/build_datasets.py 重建测试集。

文档就是包根目录的 README.md，里面有目录、怎么跑、和 8.31 的差别。结果写在 reports/report_rule_only.json 和 reports/table_row_causal_chain.json。这里要说明白：仓库里那份规则结果目前只执行了 3 条样例，通过率 100%，不是 437 条的全量成绩，不能和 8.31 的 82.15% 直接比。5.31 和 8.31 任务也不一样：5.31 是给好事件再分类，8.31 是要从事件里把链切出来。

## 第二部分：8.31causal_chain

8.31 是在 5.31 拆条之上的增强版。拆条从 chain4 换成 chain6，并且加上集锦 chain8，同时支持离线和在线。下面仍按代码、数据集、其他文档三部分讲。

## 一、代码介绍

代码分两个模块。

第一个是拆条，目录在 algo/causal_chain6。它把一段事件判成四类里的一类：结果链、修正链、险情链，或者特殊链。用法有两种。离线是整段一次给进去，直接出链。在线是事件按时间一个一个到达，程序只能看已经发生的，不能用未来事件。在线入口是 OnlineStripEngine。

第二个是集锦，目录在 algo/causal_chain8。它不重新决定“这场有哪些事件”，而是在事件时间线上按规则选出高光短窗，再对短窗做分类，得到集锦片段。片段之间可以标三种关系：前后跟随、同一段序列、后一条修正前一条。另外有一套图，用来检查节点有没有丢、有没有重复、会不会成环、顺序和修正方向对不对。这套检查我们叫结构通过。结构通过只说明图是完整的，不能当成内容和标注对上了。内容和标注对上，单独叫逻辑完整率，评的是集锦片段，不是这张图上的全部节点。

正式评测有四个脚本，都在 eval 目录，默认用规则，不加载大模型。分别是：离线拆条、离线集锦、在线拆条、在线集锦。也可以一条命令按这个顺序全跑：python eval/run_causal_chain_selftest.py，默认 63 场。

一条预测算不算对，规则是固定的，而且一对一，一条预测最多对一条标准答案。四条都要满足：时间有重叠，类别一样，开头事件一样，结尾事件一样。

按这个口径，规则版全量结果是：离线拆条，437 条里对上 359 条，逻辑完整率 82.15%，精确率 93.01%。在线拆条，437 条里对上 313 条，逻辑完整率 71.62%，精确率 72.79%。在线一半结果大约 60 秒内出来，百分之九十大约 167 秒，超过 45 秒的大约 68%，主要受窗口长度影响。离线集锦 172 条里对上 105 条，61.05%；只看人工标注的 114 条，是 57.02%。在线集锦逻辑完整率目前是 0，内容还没对上；结构检查是通过的，离线 63 场全过，在线有数据的 60 场也全过。大模型辅助分类我们试过，在线拆条只从 71.62% 到 71.85%，提升很小，所以默认仍用规则。

## 二、数据集介绍

有测试集，在包里的 datasets 目录，一共 63 场，由交付标注加工而来，回放和空类别已经去掉。

每一场一个文件夹，里面主要是这些文件。timeline.json 是整场事件时间线。strip_gold.json 是拆条的标准答案，一共 437 条。类别上险情 218 条，结果 160 条，特殊 48 条，修正 11 条。highlight_gold_no_t2.json 是集锦的标准片段，正式评测优先用这个；旁边还有一个不带 T2 限制的版本。

集锦标签有两个来源，结果里是分开报的。annotation 是附近能对上的人工标注，大约 114 条。timeline_heuristic 是对不上人工标注时，用时间线启发式补的，大约 58 条。

考核因果链这个模块本身时，我们用标注里自带的事件，不直接用检测器整场时间线当输入。检测器还会漏事件、打错类型、时间对不齐，那些问题不记在因果链模块上。

总表在 datasets/index.json，可以查场次数和各类条数。

## 三、其他文档

包里除了代码和数据，还有这些材料，都和今天讲的口径一致。

README.md 是总说明，包括怎么跑、判定规则、上面这组数字，以及评测 JSON 每个字段什么意思。algo/causal_chain6/COMMANDS.md 和 algo/causal_chain8/COMMANDS.md 是拆条、集锦的常用命令。reports 目录是跑完评测写出来的结果。总表是 reports/causal_chain_selftest_summary.json，看里面的 summary_table 即可。四个分项各自还有一个 JSON。

读结果时抓住这几个词就行。gold 是标准答案条数，也就是分母。matched 是一对一严格对上的条数。logic_rate 是逻辑完整率，就是 matched 除以 gold。precision 是命中占预测的比例。latency 是在线第一次对上的等待时间，单位毫秒。p5_structural 是结构检查，不要把它说成逻辑完整率。如果 logic_rate 是空，表示这批没有有效的集锦标准答案，这时只能讲结构，不能讲完整率。

代码在内部仓库 soccer-highlight-algorithm 里，8.31 和更早的 5.31 是两个目录，今天的数字只针对 8.31、规则版、63 场。

我的介绍就到这里。代码、数据、文档这三块如果要展开，我们可以对着包里的 README 和结果 JSON 继续对。
