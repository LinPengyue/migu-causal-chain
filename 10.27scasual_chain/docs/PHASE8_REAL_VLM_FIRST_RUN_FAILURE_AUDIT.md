## Code-grounded findings
1. **P0 — Two meanings of VERIFIED are mixed.** `story_evidence_search.py::verify_search_candidate` only checks source PTS, event-chain LIVE metadata, confidence and protected-goal overlap, then `run_story_evidence_search` calls rows `verified_candidates`. In `story_revision_planner.py::_intents_from_verified_search`, this is described as `LIVE-verified` footage. It is *not* authenticated first-broadcast video evidence, so an executable revision can be selected before the first-live ledger is checked later in `story_e2e_agent.py`.
2. **P0/P1 — Planner non-mutation may be overridden by Search fallback.** `story_e2e_agent.py` after `run_llm_revision_planner`: if the LLM returns no mutating intents but `search_backed=True`, it retains Search's executable REVISE and writes note `llm_returned_no_mutating_intents; retained_search_bound_revise`. This is an intentional rule but may contradict a real Planner decision `mark_unresolved`; investigate exact `llm_revision_planner.json`, merged `revision_plan.json` and fallback notes in both rounds before claiming it caused the repeated bridge. Do not silently treat `mark_unresolved` as approval of search_add.
3. **P1 — Search relevance is event-type/rank, not demonstrated story causality.** `_rank_events_in_window` ranks by event scores, type keyword hits, LIVE metadata and slight temporal proximity. It does NOT establish whether this footage provides narrative information connecting the two specific adjacent story beats. This is consistent with the human assessment that the 3504 bridge lengthened the edit without a clear causal buildup. Verify with the supplied candidate video, not only scores.
4. **P1 — Same-window repeat is not a demonstrated new revision.** User reports candidate EDL SHA identical in rounds 1 and 2. Inspect feedback_memory + plan/EDL + reobserve files to distinguish an intentional observational round from accidental repeated apply. `story_revision_feedback.should_penalize_candidate` suppresses matching PTS and issue context when no new *observation-grade* evidence; verify actual failure_class, action and issue_signature matching rather than assuming filtering worked.
5. **Evidence lineage and positive certificates.** User attested first-live for EXACT source PTS windows 6400.90–6412.50 and 2273.20–2290.41 (see USER_FIRST_LIVE_REVIEW_ATTESTATION.json). 3504.14–3515.83 was not certified and must remain UNKNOWN. No automatic transfer of certificates by event type, scene similarity or adjacent PTS.
